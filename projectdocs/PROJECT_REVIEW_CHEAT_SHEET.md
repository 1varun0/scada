## 1. The Core Problem
**Talking Point:** "Traditional machine learning (ML) Intrusion Detection Systems (IDS) applied to industrial control systems (ICS/SCADA) face two major problems: they generate too many false positives during normal operational transients, and they are easily fooled by sophisticated attackers who inject data that looks statistically 'normal' but violates physical laws."

**The Solution:** "We built a Hybrid IDS. Instead of relying solely on an ML black box, we incorporated deterministic engineering knowledge. We built a Digital Twin that calculates the physics, and a Policy Engine that checks the control logic. We fuse these deterministic engines with an LSTM Autoencoder to get the best of both worlds."

## 2. Methodology & Stack
- **Simulated Environment:** Stored dataset generated by the MATLAB scripts in matlab/ and imported with scripts/import_matlab_csv.py; the live plant uses the Python simulator. Generated 150 scenarios (60 normal + 90 attack) at 1Hz.
- **Deep Learning Model:** PyTorch LSTM-Autoencoder. Trains on normal data to minimize reconstruction loss.
- **Database:** SQLite (`scada_ids.db`) stores the generated telemetry for downstream processing.
- **Frontend Dashboard:** Built with Flask, Vanilla JS, and Chart.js featuring a modern, glassmorphic dark-theme UI.

### Threshold Selection Methodology
All detection thresholds were calibrated strictly on normal baseline operational data or engineering specifications; **zero attack scenarios were used for threshold selection**:
- **$\tau_p = 0.035\text{ m}$ (Physics):** Set to $0.035\text{ m}$ in `config/parameters.py` (which is exactly $2\times$ the E0 p99 residual of $0.0175\text{ m}$; no derivation formula exists in the code or git history). Over the 9 held-out normals (9,000 ticks), the maximum batch residual is $0.0288\text{ m}$ (p99 = $0.0210\text{ m}$). Recomputed across all 60 normal scenarios in the DB (60,000 ticks) using the batch physics path, the maximum residual is **0.034884 m** vs $\tau_p = 0.035\text{ m}$ (a narrow **0.3% margin**), with 0 ticks exceeding $0.035\text{ m}$. Setting $\tau_p = 0.035\text{ m}$ yields zero false positives on the 60 stored normals (0.3% margin) (~1,000 s horizons). Note that under the dataset's clamped flow noise, the twin residual crosses $\tau_p$ from about tick 861 in a 30-minute run (producing 12 physics flags between $t=861$ and $1799$), meaning the physics threshold is valid for ~1,000 s scenario runs.
- **$\tau_l = 0.0085$ (Temporal/LSTM):** Set to the maximum reconstruction error observed on the normal validation split (`df_val` from the 51 normal training/validation scenarios) to ensure normal operating dynamics stay below threshold. No attack data was used.
- **$\tau_a = 1500.0\text{ ms}, \tau_{a,max} = 5000.0\text{ ms}$ (Availability):** Established directly from SCADA network timing SLAs: at a 1 Hz polling rate, 1,500 ms flags a delayed/dropped packet, and 5,000 ms flags plant offline / complete communication loss. No attack data was used.

### Important Clarifications & Limitations

1. **Policy v2 Evolution**: The original batch evaluation table uses Policy v1. The results above for Policy v2 are from a separate offline evaluation. Policy v2 introduces a strict rule derived from the controller's engineering specification: **The valve must be at its default operating position (50%) or legitimately in its fail-safe position (0% with pump OFF)**. Any other valve position immediately triggers an alarm.
2. **Auth Misuse (A4) Detection**: Policy v2 catches 100% of A4 attack ticks. The rule was refined after inspecting attack data to include the fail-safe valve exemption (valve=0 is allowed only if pump is off). Event-Level Recall is also 100% because the LSTM reliably spikes to 1.0 during the attack window.
3. **Start-up Transients & Dataset Limitations**: While there are 0 false alarms on normal scenarios, our model *does* throw false positives before attacks (start-up flags) in scenarios starting at 0.4m or 2.1m. In fact, a settled-period start-up transient occasionally exceeds the 0.95 threshold (e.g., scoring 0.96) in scenarios starting near 2.1m. This exposes a dataset limitation: normal scenarios only start at 1.0m, 0.8m, and 0.5m. The model has never seen high starts such as 2.1m, and normal levels top out near 1.7m.
4. **Physics FPR Artifacts (DoS and Auth Misuse) & MATLAB Generator Provenance**: The 21.2% pooled FPR is overwhelmingly caused by Physics engine false alarms during A3 and A4 scenarios. Investigation of the MATLAB generators (`apply_fdi.m`, `apply_replay.m`, `apply_dos.m`, `apply_auth_misuse.m` in `matlab/run_all_scenarios.m`) reveals that **every stored attack is an open-loop post-hoc overlay on a completed normal simulation from `run_single_scenario.m`, not a closed-loop simulation**:
   - **DoS (A3)**: `apply_dos.m` overwrites telemetry during $[t_{start}, t_{end}]$ setting `packet_received=0`, $q_{in}=0, q_{out}=0, dH=0$ (level frozen). Crucially, at $t > t_{end}$, it sets `H = -1` and stops modifying the table. For all subsequent timesteps ($t > t_{end}$), the telemetry table abruptly retains the unattacked normal trajectory where the tank had continued filling at ~1.5 mm/s. Consequently, the observed level jumps up to the uninterrupted-fill trajectory (about 1.5 mm/s $\times$ duration: 3 cm to 17 cm) within 1 to 5 ticks (A3_010: 1.022 to 1.189 m in one tick; A3_001 converges in about 5 ticks). The Digital Twin, which open-loop integrates the reported zero flows during DoS, falls behind by $\approx \text{duration} \times \text{net fill rate}$ and cannot follow that jump, remaining permanently offset and triggering 7,561 false positive ticks. (The 20-tick difference between 7,541 in streaming replay and 7,561 in batch evaluation was fully reconciled: batch evaluation in `scripts/run_evaluation.py` initialized the physics engine with deterministic nominal initial level $H_0 = 1.0\text{ m}$, whereas streaming replay initialized from the noisy sensor observation at $t=0$; when initialized with the exact nominal level, streaming replay matches batch evaluation tick-for-tick across all 15 scenarios, yielding exactly 7,561 ticks).
   - **Auth Misuse (A4)**: `apply_auth_misuse.m` re-simulates physics locally during $[200, 300]$, but at $t=301$ resets `H = -1` and stops modifying rows. The telemetry table instantly reverts to the unattacked normal trajectory, causing the observed level to teleport by up to ~0.3 m in 1 second. The continuous twin expects physical continuity and refuses to teleport, creating a permanent residual across all remaining ticks (10,485 false positive ticks).
   - **Contradictions with `DATASET_DOCUMENTATION.md`**:
     1. *A1 FDI (§4.2)*: Doc claims *"Forces controller to prematurely cut pump, inducing progressive tank drainage."* Contradiction: `apply_fdi.m` is a post-hoc overlay applied after `run_single_scenario.m` finishes. The recorded controller commands (`pump_command`, `valve_command`) were generated during the normal run and never saw the spoofed level; the controller was never forced to cut the pump.
     2. *A3 DoS (§4.2)*: Doc claims *"Outflow drops to 0, locking the remaining water volume in the tank."* Contradiction: `apply_dos.m` only freezes level during the attack window; at $t > t_{end}$, it abruptly drops back into the unattacked filling trajectory rather than continuing closed-loop from the locked volume.
     3. *A4 Auth Misuse (§4.2)*: Doc describes catastrophic continuous failure modes (complete drainage / cavitation risk, structural overflow). Contradiction: `apply_auth_misuse.m` abruptly snaps back to the normal steady-state trajectory at $t=301$, completely erasing the accumulated drainage/overflow.
     4. *Simulation Pipeline (§2.1)*: Step 3 claims closed-loop controller decisions react to conditions, but Step 7 applies open-loop post-processing overlays without closing the loop back to the controller or continuing physics after $t_{end}$.
5. **Step 2b DoS Gap Re-Seed Rule & Limitation**: In `StreamingIDS` (`dos_gap_rule=True`, default False for Phase 2 equivalence), after a DoS gap of $G$ ticks with `received=False`, the twin does not re-seed on a single packet. Instead, it collects $K=5$ consecutive valid post-gap readings, verifies stability ($\text{std} \le \text{max\_std\_m} = 0.03\text{ m}$), and checks if the median $m$ satisfies physical rate bounds: $|m - h_{twin}| \le v_{max} \cdot G \cdot dt + 3\sigma_{sensor}$, where $v_{max} = \max(q_{in,max}/A, C_v \sqrt{h_{max}}/A) = 0.003162\text{ m/s}$ and $\sigma_{sensor} = 0.005\text{ m}$. If within the band, the twin re-seeds to $m$, clearing the post-gap residual; if outside or if collection times out after `gap_collect_timeout_ticks` (20 ticks), re-seed is refused and physics takeover engages. **Limitation**: A spoof within $v_{max} \cdot G \cdot dt + 3\sigma_{sensor}$ after a gap is adopted by the twin. This rule bounds physically impossible jumps, but the command-driven shadow estimator in Phase 6c (which tracks actual physical valve/pump commands rather than integrating reported flows or blind re-seeding) is the true structural fix.

### Physical Parameter Mismatch & Drift Sensitivity (Horizon T = 2400 s)
- **Harness Handback Tolerance:** The harness uses config **0.05 m** (`cfg.prevention.handback_tolerance_m = 0.05`) loaded by `GatewayCore`. This value accounts for $3\sigma$ sensor noise ($1.5\text{ cm}$) plus minor open-loop twin integration divergence, ensuring smooth hand-back when sensor bias returns to zero while preventing premature hand-back during active spoofing.
- **Twin Invariance to Valve $C_v$ Errors:** The Digital Twin integrates mass conservation directly from flow-meter telemetry: $\frac{dh_{twin}}{dt} = \frac{Q_{in} - Q_{out}}{A}$. While valve $C_v$ variations alter the plant's physical discharge hydraulics, the plant discharge flow-meter measures the resulting outflow $Q_{out}$ and supplies it to the twin. Consequently, valve $C_v$ errors cannot affect the digital twin's mass balance. Only flow-sensor calibration biases ($\Delta Q / A$) and tank cross-sectional area mismatches ($\Delta A$) induce twin drift.
- **Linear Growth of Flow-Sensor Bias:** With a 5% flow-sensor bias on nominal flow $Q_{in} = 0.002\text{ m}^3\text{/s}$ in a tank with area $A = 2.0\text{ m}^2$, the rate of level error accumulation is:
  $$\frac{dh}{dt} = \frac{\Delta Q_{in}}{A} = \frac{0.05 \times 0.002\text{ m}^3\text{/s}}{2.0\text{ m}^2} = 0.00005\text{ m/s} = 0.05\text{ mm/s}$$
  Over a full simulation horizon of $T = 2400\text{ s}$, the worst-case continuous filling drift is $\Delta h = 2400 \times 0.05\text{ mm/s} = 0.12\text{ m} = 12\text{ cm}$ (or $\approx 6\text{ cm}$ at typical 50% pump duty cycle).
- **Relationship to `max_degraded_s` (600 s):** In live SCADA deployment, open-loop twin takeover is bounded by a watchdog timeout `max_degraded_s = 600\text{ s}` before transitioning to plant fail-safe. Over 600 s of continuous takeover, the maximum drift from 5% flow mismatch is:
  $$\Delta h_{600s} = 600\text{ s} \times 0.05\text{ mm/s} = 30\text{ mm} = 3.0\text{ cm}$$
  This 3.0 cm deviation is safely absorbed inside the $[0.8, 1.2\text{ m}]$ operational deadband, proving that parametric mismatch does not breach safety boundaries ($0.3\text{ m}$ or $2.5\text{ m}$) during degraded operation.

## 4. Technical Challenges Overcome
Be prepared to discuss these challenges that you successfully debugged and fixed during the project:

1. **Twin Tracking Bias:** During our 30-minute live soak tests, the Digital Twin slowly drifted out of bounds. The clamp `max(0, Q + noise)` is part of the dataset noise spec; it creates a twin bias that is negligible within 1,000 s but exceeds `tau_p` after about 25 to 30 minutes. Long live demos use zero-mean noise as a deliberate deviation to eliminate the bias.
2. **Digital Twin Initialization Bias:** The Physics Digital Twin was originally initializing its starting state (`H_0`) by reading the very first *noisy* sensor reading. This meant the twin started with an inherent error offset, throwing off the physical residual. We fixed this by providing the twin with the *deterministic* initial state configuration.
3. **Policy Engine Thresholding:** The Policy Engine originally threw false positives during normal operation because it used strict inequalities (`>` instead of `>=`), conflicting with the tank's acceptable deadband. We fixed the control logic boundary rules.
4. **Performance Bottlenecks:** Initially, the evaluation loop was taking 35+ minutes because the Temporal Engine was instantiating a new pandas DataFrame for every single row. We optimized this by pre-allocating NumPy arrays, reducing evaluation time to ~5 minutes.
5. **Fusion Strategy Dilution:** We initially used a `weighted_sum` fusion strategy. This caused attacks like FDI to be completely missed because they only triggered one engine (maxing at 0.25, failing to cross 0.5). We switched to a `max_vote` strategy (`S_hybrid = max(engines)`), which perfectly captured these domain-specific attacks.
